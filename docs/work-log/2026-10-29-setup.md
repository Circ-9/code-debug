# 2026-10-29 开发环境搭建与第一次内核断点

## 目标

搭起「QEMU 跑内核 + gdb 远程连接」的最小环境，验证源代码级调试链路可用。

## 环境

- Windows 11 + WSL2（Ubuntu 24.04，20 核）
- QEMU 8.2.2
- gdb-multiarch 15.1
- riscv64-unknown-elf-gcc 13.2.0
- 被调试内核：xv6-riscv（MIT）

## 完成的事

1. 安装 QEMU、gdb-multiarch、RISC-V 交叉工具链；
2. 克隆并编译 xv6-riscv，生成带调试信息的 `kernel/kernel` 和 `fs.img`；
3. 用 `-S -gdb tcp::26000` 启动 QEMU，gdb 通过 `target remote :26000` 连接；
4. 在 `syscall` 与 `usertrap` 下断点并成功命中，验证了「地址 → 源码行」的符号解析。

## 实测输出

```
(gdb) break syscall
Breakpoint 1 at 0x80002886: file kernel/syscall.c, line 138.
(gdb) continue
Continuing.
Thread 3 hit Breakpoint 1, syscall () at kernel/syscall.c:138
138	{
(gdb) bt
#0  syscall () at kernel/syscall.c:138
#1  0x0000000080002640 in usertrap () at kernel/trap.c:68
#2  0x0000003ffffff09c in ?? ()
(gdb) info registers pc
pc             0x80002886	0x80002886 <syscall>
```

## 观察

- 内核代码运行在 `0x8000_0000` 以上的高地址，用户程序在低地址；两者的符号表是分开的。
- `bt` 中 `#2 0x0000003ffffff09c in ?? ()` 显示 `??`，是因为当前只加载了内核符号表，无法解析用户程序的地址。
  **这正是赛题中「断点组」与「符号表切换」机制存在的原因。**

## 遇到的问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `panic: could not find virtio disk` | 新版 QEMU 的 virtio-mmio 默认非 legacy | 启动参数加 `-global virtio-mmio.force-legacy=false` |
| gdb `continue` 后立即报 `Cannot execute this command while the target is running` | 命令从非终端输入，`continue` 未阻塞 | 用 `script -q -c` 分配伪终端后再喂命令 |
